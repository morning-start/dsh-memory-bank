## 1. 四个真 bug

### 1.1 七条密钥规则从来没生效过

**症状**：G3 安全门「通过」，但 `api_key=` / `app_secret=` / `password:` / `Bearer` 一个都没拦住。

**根因**：规则表是从 Python 实现的 OwnMem 抄过来的，其中 7 条带内联标志 `(?i)`：

```js
'(?i)\\bapi[_-]?key\\s*[:=]\\s*[A-Za-z0-9_\\-]{16,}'
```

而 JS 里 `new RegExp('(?i)...')` 是 **SyntaxError**。调用方写法：

```js
try { regex = new RegExp(pattern, pattern.startsWith('(?i)') ? '' : 'u') }
catch { continue }        // ← 静默吞掉
```

于是这 7 条**每一条都编译失败、每一条都被跳过**。

**为什么严重**：G3 是整个协议里唯一不可协商的门 —— 其余九道门都可以降级、可以 `DEFER`，只有它必须硬拒。

> **一条永远不匹配的密钥规则比没有规则更糟：它让「我们扫过密钥」这句话变成谎话。**

**修法**：`compileRule` 显式剥掉开头的内联标志组、转成 JS 的 flags 参数。导出给 `promote.js` 共用 —— 两处必须用**同一个**编译器，否则又是一次漂移。

**回归**：`assertRulesCompile()` + 五个密钥族逐个命中。

```bash
node --test test/promote.test.mjs
```

### 1.2 回执层从未生效 —— 每条记忆都被判成 `tampered`

**症状**：`memory_audit` 对每一条正常写入的记忆报「回执异常 · 正文被改」。

**根因**：正文往返多了一个换行。

```
serializeEntry: lines.push('---', '', entry.body.trimEnd(), '')  → ...正文\n
parseEntry:     normalized.slice(end + 5).replace(/^\n+/, '')    → ...正文\n  ← 没剥
contentHash:    body: entry.body                                  ← 原始 body
```

于是 `contentHash(写回值) !== contentHash(读回值)`。

**为什么严重**：回执/内容寻址是整个设计的地基（「记忆随仓库 review、随回滚消失」全靠它）。而且它的报警文案是「正文被改」——

> 它对着每一条**正常写入**的记忆，做了一次**虚假的篡改指控**。
> 那比没有回执更糟：它训练用户忽略这个警告。

**修法**：`canonicalBody()` 成为**写入 / 解析 / 哈希三处共用的唯一规范形式**（CRLF → LF，去尾部空白）。

**回归**：`contentHash(parseEntry(serializeEntry(x))) === contentHash(x)`。

```bash
node --test test/drift.test.mjs
```

### 1.3 G8 把 `confidence` 标签当成分数，静默丢弃记忆

**症状**：跑 G1 基准时，「文档里没有、值得记」的 5 条候选全部 `DEFER` 而不是 `ACCEPT`。

**根因**：`confidence` 这个字段名被两个东西共用：

| 谁 | 是什么 |
|---|---|
| 条目上的 `confidence` | **标签** `verified` / `inferred` / `stale`（进 frontmatter） |
| 门要的 | **分数** 0–1（由五项算出来） |

```js
const confidence = candidate.confidence ?? computeConfidence(candidate)   // ← 错
```

只要调用方带了标签（schema 完全允许，`memory_resolve` 的编辑路径本来就会带），比较变成 `'verified' >= 0.6` → 恒为 false → 掉进 `confidence.low` 分支 → 返回 `discard: true`：

> **不建提案、不落盘、只剩一行日志没人看。**
> 静默丢弃一条本该记住的记忆，是这个系统最坏的失败方式 ——
> 用户不知道它发生了，只会觉得「这插件好像什么也没记住」。

**修法**：只有 `typeof candidate.confidence === 'number'` 时才当分数用。

**为什么一直没被发现**：生产路径不带标签，**只有基准会带**。

### 1.4 捕获阻塞回合关闭 92 ms

**症状**：`agent/turn-stopping` 是宿主 **await** 的路径 —— 它花多少，用户就多等多少才看到回合结束。

```
旧实现   foldTurn + collectOwners + review + writeEntry + ensureSnapshot(force)   92 ms
         其中 90 ms 是 ensureSnapshot(force) —— 为了加一条记忆，把 200 条索引整个重编
```

**修法**：

1. **收件箱落盘**（`.dsh-memory/inbox/`）—— turn-stopping 只做「确定性判定 + 落盘入队」，十道门交给后台 drain。落盘而不是纯内存队列：进程崩掉时内存队列丢数据，而「这条记忆该记」是你在那一轮里刚说出口的东西。
2. **索引重建挪到后台**（`markDirty`）—— 正确性不依赖后台是否跑完（读路径仍然同步校验 `contentHash`），只是把「一次写」的代价从你等回合结束，挪到你看不见的地方。
3. **owner 文档与语料关键词缓存** —— 两段式戳：目录 mtime 便宜戳命中，每 2 秒一次全量核对。

```
新实现   turn-stopping（入队）      2.4 ms   ← 宿主 await 这条
         后台 drain（门 + 写入）     1.5 ms   ← 用户看不到
```

**顺带发现的 bug**：自动捕获会写入带占位符的草稿（`# 执行\n（待补：怎么做）`），因为 G2 只检查标题在不在。新增 **G2b 草稿门**堵住。

```bash
node bench/capture.mjs
```

## 2. G1 实测：拿本仓库自己的文档当语料

```bash
node bench/g1-eval.mjs
```

5 份 owner 文档（README + `docs/*.md`，约 52,000 字），15 条候选分三组：

| 组 | 期望 | 结果 |
|---|---|---|
| **A 逐字**（文档里已经说过的断言） | 拒 | **10 / 10** |
| **B 无关**（文档里没有、值得记的事实） | 过 | **5 / 5** |
| **C 改写**（同义不同词） | 拒（会漏） | **0 / 5** |

完整十道门终审 **15 / 15** —— G1 的拒绝没被别的门盖掉，B 组真的走到了 `ACCEPT`。

### C 组 0/5 不是 bug，是方法的硬天花板

试过用**滑窗字符 n-gram 覆盖率**去救改写：

```
A 逐字   1.000
C 改写   0.000 – 0.364
B 无关   0.000 – 0.208
```

C 的最高分离 B 的最高分太近 —— 阈值卡在哪里都抓不到改写，只会开始误伤 B。

所以 G1 的能力边界是清楚的：

> **它抓的是「Agent 把文档里的一行抄进记忆」这个最常见的失败，不是语义重复。**

设计文档写的「保守实现，误判方向偏向 ACCEPT」在这个数据上成立了 —— 但「偏向 ACCEPT」的代价是**改写一律漏过**，这一点现在有数字了。

## 3. 语义通道：做成了，但**开闸没有依据**

### 3.1 第一次实验：余弦被窗口长度惩罚

```
A 逐字（该拒）  最低 0.079   ← 逐字的怎么会这么低？
```

因为 5 个 token 的候选对上 50 个 token 的窗口，`dot ≈ 1/√50 ≈ 0.14`。

> **分数低不代表不包含，只代表窗口长。** 这是度量的错，不是方法的错。

### 3.2 第二次实验：加权包含度

改问「这段文档**拥有**这条断言吗」——是**包含**关系，不是相似关系：

```
containment(a, b) = Σ_{t∈a} w_a[t]·[t∈b] / Σ_{t∈a} w_a[t]
```

```
A 逐字（该拒）  最低 0.264
B 无关（该过）  最高 0.200
C 改写（该拒）  最低 0.204
分离 = +0.004
```

**+0.004 不是分离，是 15 个手挑样本上的巧合。** 拿它开闸就是拿误伤换漏报，而且用户会以为自己买到了召回。

### 3.3 所以：可插拔 + 默认关 + 开闸有标准

```bash
node bench/embedding-experiment.mjs
# 看最后一行：分离（C 最低 - B 最高）
#   < 0.05  不要开。任何阈值都是噪音。
#   ≥ 0.15  可以考虑。阈值取两组的中间值，把数字写进 commit message。
```

| provider | 状态 |
|---|---|
| `none` | **默认。** G1 走逐字包含 |
| `lexical` | 本地确定性向量，**实测不足以做 G1 判决**，只做诊断 |
| `http` | 唯一可能真的有效的实现（OpenAI 兼容 `/embeddings`） |

**架构上的硬约束**：`recall` 和 `gate` 都是同步的（每轮 prompt 装配），而 HTTP 是异步的。所以 embedding **不在门里调用**，它是**可预先计算的数据**：

```
语料向量   → 算一次，挂在 owners 数组上（WeakMap）
候选向量   → 在 memory_remember / 后台 drain（本来就是 async）里算
门         → 只做同步余弦；拿不到向量就退回逐字包含
```

**默认路径仍然是同步的。** 只有通道真的开着、而且配了 `g1Threshold` 时 `memory_remember` 才返回 Promise。这不是为了性能，是为了**诚实**：默认配置下的行为和以前逐字节相同，任何一个老测试的通过或失败都还是它自己说的那件事。

## 4. 性能

两百条记忆 / 305 个词表：

```
装配路径（每轮 prompt 都跑）
  冷启动（无缓存）        ensureSnapshot                117 ms
  热路径（缓存命中）      ensureSnapshot                0.66 ms
                          recall（5 路 + RRF + MMR）    3.97 ms
                          每轮合计                      4.62 ms

捕获路径（宿主 await 回合关闭）
  旧实现                  同步跑完整条链                 92 ms
  新实现                  turn-stopping（入队）          2.4 ms
                          后台 drain（门 + 写入）        1.5 ms
```

```bash
node bench/assembly.mjs
node bench/capture.mjs
```

三处优化，都在**每轮**路径上：

1. **扫描缓存**用「便宜戳 + 定期全量核对」：目录 mtime 1 次 `statSync` 命中；每 2 秒才跑一次逐文件全量戳。最坏是外部编辑器改了一行、2 秒后才被看见 —— 在这个系统里，2 秒的陈旧远远好过每轮多付 3 毫秒。
2. **快照缓存**按指针内容失效（只有本进程会发布，指针就是充分信号）。
3. **派生集合**（字段 token / 3-gram / MMR 指纹 / 归一化 exact-map / 邻接表）全部 `WeakMap` 挂在对象上，快照换对象时自然回收。

> 数字只用于判断「这个优化值不值得」，**不作为性能承诺** —— 磁盘、杀毒软件、文件系统都会大幅改变绝对值。
