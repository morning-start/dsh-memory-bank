## 1. 四个真 bug

### 1.1 七条密钥规则从来没生效过

**症状**：G3 安全门「通过」，但 `api_key=` / `app_secret=` / `password:` / `Bearer` 一个都没拦住。

**根因**：规则表是从 Python 实现的 OwnMem 抄过来的，其中 7 条带内联标志 `(?i)`：

```js
'(?i)\\bapi[_-]?key\\s*[:=]\\s*[A-Za-z0-9_\\-]{16,}'
```

而 JS 里 `new RegExp('(?i)...')` 是 **SyntaxError**。调用方写法：

```js
try { regex = new RegExp(pattern, pattern.startsWith('(?i)') ? '' : 'u') }
catch { continue }        // ← 静默吞掉
```

于是这 7 条**每一条都编译失败、每一条都被跳过**。

**为什么严重**：G3 是整个协议里唯一不可协商的门 —— 其余九道门都可以降级、可以 `DEFER`，只有它必须硬拒。

> **一条永远不匹配的密钥规则比没有规则更糟：它让「我们扫过密钥」这句话变成谎话。**

**修法**：`compileRule` 显式剥掉开头的内联标志组、转成 JS 的 flags 参数。导出给 `promote.js` 共用 —— 两处必须用**同一个**编译器，否则又是一次漂移。

**回归**：`assertRulesCompile()` + 五个密钥族逐个命中。

```bash
node --test test/promote.test.mjs
```

### 1.2 回执层从未生效 —— 每条记忆都被判成 `tampered`

**症状**：`memory_audit` 对每一条正常写入的记忆报「回执异常 · 正文被改」。

**根因**：正文往返多了一个换行。

```
serializeEntry: lines.push('---', '', entry.body.trimEnd(), '')  → ...正文\n
parseEntry:     normalized.slice(end + 5).replace(/^\n+/, '')    → ...正文\n  ← 没剥
contentHash:    body: entry.body                                  ← 原始 body
```

于是 `contentHash(写回值) !== contentHash(读回值)`。

**为什么严重**：回执/内容寻址是整个设计的地基（「记忆随仓库 review、随回滚消失」全靠它）。而且它的报警文案是「正文被改」——

> 它对着每一条**正常写入**的记忆，做了一次**虚假的篡改指控**。
> 那比没有回执更糟：它训练用户忽略这个警告。

**修法**：`canonicalBody()` 成为**写入 / 解析 / 哈希三处共用的唯一规范形式**（CRLF → LF，去尾部空白）。

**回归**：`contentHash(parseEntry(serializeEntry(x))) === contentHash(x)`。

```bash
node --test test/drift.test.mjs
```

### 1.3 G8 把 `confidence` 标签当成分数，静默丢弃记忆

**症状**：跑 G1 基准时，「文档里没有、值得记」的 5 条候选全部 `DEFER` 而不是 `ACCEPT`。

**根因**：`confidence` 这个字段名被两个东西共用：

| 谁 | 是什么 |
|---|---|
| 条目上的 `confidence` | **标签** `verified` / `inferred` / `stale`（进 frontmatter） |
| 门要的 | **分数** 0–1（由五项算出来） |

```js
const confidence = candidate.confidence ?? computeConfidence(candidate)   // ← 错
```

只要调用方带了标签（schema 完全允许，`memory_resolve` 的编辑路径本来就会带），比较变成 `'verified' >= 0.6` → 恒为 false → 掉进 `confidence.low` 分支 → 返回 `discard: true`：

> **不建提案、不落盘、只剩一行日志没人看。**
> 静默丢弃一条本该记住的记忆，是这个系统最坏的失败方式 ——
> 用户不知道它发生了，只会觉得「这插件好像什么也没记住」。

**修法**：只有 `typeof candidate.confidence === 'number'` 时才当分数用。

**为什么一直没被发现**：生产路径不带标签，**只有基准会带**。

### 1.4 捕获阻塞回合关闭 89–113 ms

**症状**：`agent/turn-stopping` 是宿主 **await** 的路径 —— 它花多少，用户就多等多少才看到回合结束。

```
旧实现   foldTurn + collectOwners + review + writeEntry + ensureSnapshot(force)   89–113 ms
         其中 ~90 ms 是 ensureSnapshot(force) —— 为了加一条记忆，把 200 条索引整个重编
```

**修法**：

1. **收件箱落盘**（`.dsh-memory/inbox/`）—— turn-stopping 只做「确定性判定 + 落盘入队」，十道门交给后台 drain。落盘而不是纯内存队列：进程崩掉时内存队列丢数据，而「这条记忆该记」是你在那一轮里刚说出口的东西。
2. **索引重建挪到后台**（`markDirty`）—— 正确性不依赖后台是否跑完（读路径仍然同步校验 `contentHash`），只是把「一次写」的代价从你等回合结束，挪到你看不见的地方。
3. **owner 文档与语料关键词缓存** —— 两段式戳：目录 mtime 便宜戳命中，每 2 秒一次全量核对。

```
新实现   turn-stopping（入队）      2.4–3.3 ms   ← 宿主 await 这条
         后台 drain（门 + 写入）     1.5–1.9 ms   ← 用户看不到
```

**顺带发现的 bug**：自动捕获会写入带占位符的草稿（`# 执行\n（待补：怎么做）`），因为 G2 只检查标题在不在。新增 **G2b 草稿门**堵住。

```bash
node bench/capture.mjs
```

## 2. G1 实测：拿本仓库自己的文档当语料

```bash
node bench/g1-eval.mjs
```

5 份 owner 文档（README + `docs/*.md`，约 52,000 字），15 条候选分三组：

| 组 | 期望 | 结果 |
|---|---|---|
| **A 逐字**（文档里已经说过的断言） | 拒 | **4 / 10** |
| **B 无关**（文档里没有、值得记的事实） | 过 | **5 / 5** |
| **C 改写**（同义不同词） | 拒（会漏） | **0 / 5** |

完整十道门终审 **9 / 15**，精度 **60.0%** ——
G1 只拒掉了 `a5` / `a6` / `a8` / `a9` 四条，其余六条它**放行**；
B 组 5 条全部走到 `ACCEPT`（判对），C 组 5 条全部漏过（预期内）。

> **0.1.0 的文档写的是「逐字 10/10 · 完整协议 15/15」。那是错的。**
> 0.1.0 之后的文档改过几轮，A 组用例是**照改之前的文档写的**，没有人重跑基准。

### A 组 4/10 的已知限制（0.1.1 仍未修）

`a1` / `a2` / `a3` / `a4` / `a7` / `a10` 六条的 `title` 在**现文档里不是逐字子串**，
所以 G1 放行。G1 实现的判据只有 1/2（规则文件 + 权威文档的**完全包含**），
判据 3/4/5（回归测试索引 / 符号索引 / 同 id 前缀）**没有实现**。

两条路，二选一：

1. 重写 A 组用例，用**当前**文档里的原文（这样 4/10 会变成 10/10，但那是**改考题**）；
2. 承认 G1 只抓「Agent 把文档里的一行**逐字**抄进记忆」这个最常见的失败 —— 现在就是这条路。

**0.1.1 选了 2，并把它写进文档。** 因为改考题能做出漂亮的数字，
而漂亮的数字正是 0.1.0 那次「196 条全绿」的由来。

### C 组 0/5 不是 bug，是方法的硬天花板

试过用**滑窗字符 n-gram 覆盖率**去救改写：

```
A 逐字   1.000
C 改写   0.000 – 0.364
B 无关   0.000 – 0.208
```

C 的最高分离 B 的最高分太近 —— 阈值卡在哪里都抓不到改写，只会开始误伤 B。

所以 G1 的能力边界是清楚的：

> **它抓的是「Agent 把文档里的一行抄进记忆」这个最常见的失败，不是语义重复。**

设计文档写的「保守实现，误判方向偏向 ACCEPT」在这个数据上成立了 —— 但「偏向 ACCEPT」的代价是**改写一律漏过**，这一点现在有数字了。

## 3. 语义通道：做成了，但**开闸没有依据**

### 3.1 第一次实验：余弦被窗口长度惩罚

```
A 逐字（该拒）  最低 0.079   ← 逐字的怎么会这么低？
```

因为 5 个 token 的候选对上 50 个 token 的窗口，`dot ≈ 1/√50 ≈ 0.14`。

> **分数低不代表不包含，只代表窗口长。** 这是度量的错，不是方法的错。

### 3.2 第二次实验：加权包含度

改问「这段文档**拥有**这条断言吗」——是**包含**关系，不是相似关系：

```
containment(a, b) = Σ_{t∈a} w_a[t]·[t∈b] / Σ_{t∈a} w_a[t]
```

```
A 逐字（该拒）  最低 0.244
B 无关（该过）  最高 0.286
C 改写（该拒）  最低 0.266
分离 = -0.020
```

**−0.020 不是「没有分离」，是「这个指标测的是噪音」。** 最硬的证据是它自己会翻：

| 什么时候跑的 | A 最低 | B 最高 | C 最低 | 分离 | 脚本判决 |
|---|---|---|---|---|---|
| 0.1.0 的文档 | 0.264 | 0.200 | 0.204 | **+0.004** | （当时没判决） |
| 0.1.1 审计（改文档前） | 0.244 | 0.203 | 0.267 | **+0.063** | ✅ 可分离 |
| 0.1.1 写文档时（**当前**） | 0.244 | **0.286** | 0.266 | **−0.020** | ❌ 不可分离 |

**15 个候选一个字没动**，只因为 owner 文档（语料就是本仓库的 6 份 `.md`）改了几段，
分离度从 `+0.063` 翻成 `−0.020`。样本量 15 的情况下，这条曲线**任何一处**都能用一次编辑翻号。

判据自己也自相矛盾：`bench/embedding-experiment.mjs` 的阈值是 `> 0.05` 就报「可分离」，
而本节的规则是 `< 0.05 不要开 / ≥ 0.15 可以考虑` —— **0.063 落在 `[0.05, 0.15)` 这段
文档没给规则的缝里**，两边都能被引用来支持相反结论。

0.1.1 统一成一条（本节与 `docs/04` 已经统一；`lib/embedding.js` 文件头的**判据**也是这一条，
但里面的**数字还是旧的** `0.264 / 0.200 / 0.204 · +0.004`，**待 Lead 更新** —— 那个文件不在文档的写作用域里）：

| 分离度 | 处置 |
|---|---|
| `< 0.05` | **关**。任何阈值都是噪音。 |
| `0.05 – 0.15` | **只做诊断**：进 `memory_audit` 的近似候选列表，**不改 G1 的裁决**。 |
| `≥ 0.15` | 才允许**开闸**。阈值取两组的中间值，把数字写进 commit message。 |

按这条，**当前 −0.020 落在第一档 → 语义通道关着。**

### 3.3 所以：可插拔 + 默认关 + 开闸有标准

```bash
node bench/embedding-experiment.mjs
# 看最后一行：分离（C 最低 - B 最高）
#   < 0.05      关。任何阈值都是噪音。
#   0.05 – 0.15 只做诊断。进 memory_audit 的近似候选列表，不改 G1 的裁决。
#   ≥ 0.15      才允许开闸。阈值取两组的中间值，把数字写进 commit message。
#
# 本仓库实测 -0.020 → 第一档，通道关着。
```

| provider | 状态 |
|---|---|
| `none` | **默认。** G1 走逐字包含 |
| `lexical` | 本地确定性向量，**实测不足以做 G1 判决**，只做诊断 |
| `http` | 唯一可能真的有效的实现（OpenAI 兼容 `/embeddings`） |

**架构上的硬约束**：`recall` 和 `gate` 都是同步的（每轮 prompt 装配），而 HTTP 是异步的。所以 embedding **不在门里调用**，它是**可预先计算的数据**：

```
语料向量   → 算一次，挂在 owners 数组上（WeakMap）
候选向量   → 在 memory_remember / 后台 drain（本来就是 async）里算
门         → 只做同步余弦；拿不到向量就退回逐字包含
```

**默认路径仍然是同步的。** 只有通道真的开着、而且配了 `g1Threshold` 时 `memory_remember` 才返回 Promise。这不是为了性能，是为了**诚实**：默认配置下的行为和以前逐字节相同，任何一个老测试的通过或失败都还是它自己说的那件事。

## 4. 性能

两百条记忆 / 305 个词表：

```
装配路径（每轮 prompt 都跑）
  冷启动（无缓存）        ensureSnapshot                88–164 ms
  热路径（缓存命中）      ensureSnapshot                0.6–1.1 ms
                          recall（5 路 + RRF + MMR）    4.1–6.7 ms
                          每轮合计                      p50 4.3–7.8 ms · p95 46–90 ms

捕获路径（宿主 await 回合关闭）
  旧实现                  同步跑完整条链                 89–113 ms
  新实现                  turn-stopping（入队）          2.4–3.3 ms
                          后台 drain（门 + 拒绝）         1.5–1.9 ms
```

> **`p95` 这个标签本身不准。** `bench/assembly.mjs:90` 的 `percentile(values, p)`
> 用 `[Math.floor(len * p)]`，在 **20 个样本**上取 p95 得到的是索引 19 —— 即**最大值**。
> 所以 `p95 46–90 ms` 描述的是「最慢的那一次」，不是分位数。真正的验收指标是 **p50**。
>
> **`drain` 那一行测的是「门 + 拒绝」，不是「门 + 写入」。** `bench/capture.mjs` 的
> `drain 结果：REJECT 30` —— 30 条候选**全部被拒**，写入分支一次都没执行。
> 这个数字只能说明「拒绝路径很便宜」，不能说明「写入路径很便宜」。

```bash
node bench/assembly.mjs
node bench/capture.mjs
```

三处优化，都在**每轮**路径上：

1. **扫描缓存**用「便宜戳 + 定期全量核对」：目录 mtime 1 次 `statSync` 命中；每 2 秒才跑一次逐文件全量戳。最坏是外部编辑器改了一行、2 秒后才被看见 —— 在这个系统里，2 秒的陈旧远远好过每轮多付 3 毫秒。
2. **快照缓存**按指针内容失效（只有本进程会发布，指针就是充分信号）。
3. **派生集合**（字段 token / 3-gram / MMR 指纹 / 归一化 exact-map / 邻接表）全部 `WeakMap` 挂在对象上，快照换对象时自然回收。

> 数字只用于判断「这个优化值不值得」，**不作为性能承诺** —— 磁盘、杀毒软件、文件系统都会大幅改变绝对值。

## 7. 0.1.1 修的 8 个 P0

**这一节是这个项目最有价值的资产。**

0.1.0 发布时对外声称「196 条全绿 · G1 10/10 · P95 < 5ms」。
0.1.1 的审计把这三句话逐条推翻了 —— 而推翻的方式不是「发现了新 bug」，
是**发现那 196 条恰好测不到出 bug 的那一层**。

### 7.0 为什么 196 条测试一个都没抓到

`test/plugin.test.mjs` 是**唯一**覆盖 `apply()` 接线的测试，而它的 `Config` schema
依赖 peer 依赖 `@deepseek-ai/schemastery` —— 没装 profile 的机器上整组 `describe` 被 **skip**。

```
# 0.1.0 的 npm test 输出（关键行）
# skipped 12        ← 就是它
# tests 196
# pass 196
```

于是一个从来没跑过的测试，撑起了「196 条全绿」这个结论。更糟的是它自己也**过时了**：
断言的工具清单写的是 6 个，实际 7 个（`memory_promote` 加了但断言没改）。

**修法**：新建 `test/wiring.test.mjs`（10 条），**不碰 schemastery**，
直接调 `createToolDefinitions` / `createHooks` / `createMemoryCommand` —— 所以**永远会跑**。
`plugin.test.mjs` 那 12 条在装了 profile 的环境里仍然有价值，但它不再是唯一防线。

```bash
node --test "test/*.test.mjs" 2>&1 | Select-String '^# (tests|pass|fail|skipped)'
# tests 274 / pass 274 / fail 0 / skipped 0
```

### 7.1 `basename` 未导入 → 三条路一起 `ReferenceError`

- **现象**：`pending/` 里一个被截断的 `.json`，让 `memory_pending` / `memory_audit` / `memory_resolve` 一起崩。
- **根因**：`readProposalDir` 的 `catch` 里用了 `basename`，顶部没导入。而那个 `catch` 正是「单个坏文件不拖垮扫描」的**唯一实现**。
- **修法**：id 从文件名推导，不依赖未导入符号（`lib/store.js:608-623`）。
- **回归**：`test/capture.test.mjs` · 「坏文件不拖垮整个收件箱」。

### 7.2 「原子写」先 `rm` 再 `rename` → 读者看到的是「没有文件」

- **现象**：Windows 上写记忆偶发文件消失。
- **根因**：`writeFileAtomic` 先删目标再改名。Node 的 `renameSync` 在 Windows 上**本来就会覆盖**；多删一次，删和改名之间任何失败都让文件真的不见。
- **修法**：直接 `rename` 覆盖，失败清 tmp（`lib/util.js:52-71`）。
- **回归**：所有写路径；`test/drift.test.mjs` · 「**文件没改 → healthy**（带行号也走 anchorHash）」。

### 7.3 正文以空行开头的记忆**刚写完就判篡改**

- **现象**：`memory_audit` 报「回执异常 · 正文被改」。
- **根因**：0.1.0 只修了**尾随**换行。`parseEntry` 额外剥**前导**换行，而 `serializeEntry` / `contentHash` 不剥 —— 又一份漂移的实现。
- **修法**：`canonicalBody` 是**写入 / 解析 / 哈希三处唯一**的规范形式（`lib/model.js:288-349`、`:445`）。
- **回归**：`test/drift.test.mjs` · 「**serialize → parse 必须回到同一个 contentHash**」。

### 7.4 路径穿越：`id` 未校验就拼进路径

- **现象**：`id: "../../package"` 能把文件写出记忆库 —— 而 `memories/` 是进 git、随 PR review 的。
- **根因**：`id` 有两个不可信来源（工具参数、frontmatter），两处都直接 `join`。
- **修法**：`entryFile()` 是**唯一** id → 路径转换点，三道闸（白名单 + `resolve` 后 `relative`）（`lib/store.js:69-88`）。
- **回归**：`test/drift.test.mjs` · 「../ 逃出仓库 → unsafe-path」。

### 7.5 七个工具全部 `resolveRoot()` 不传 agent

- **现象**：在仓库 A 里说「记住 X」，记忆写到 DSH 进程 cwd，`/memory status` 读仓库 A。**两份世界。**
- **根因**：`createResolver` 里「会话工作目录」那一段是死代码。修的时候只有 `memory_remember` 一条漏网，其余 6 个是被新建的 wiring 测试**当场抓红**的。
- **修法**：七个工具统一 `resolveRoot(exec?.agent)`（`lib/tools.js:167`、`:411`、`:442`、`:504`、`:582`、`:827`、`:900`）。
- **回归**：`test/wiring.test.mjs` · 「**七个工具都把 exec.agent 传给 resolveRoot**」。

### 7.6 中文标题 id 全部塌成 `memory` → 静默覆盖

- **现象**：两条中文标题争同一个文件名，后写的静默覆盖先写的。
- **根因**：**两套 id 算法，各有一个洞** —— `normalizeId` 只判「slug 长度 < 4」（中文归一化后是空串 → `memory`）；`capture.js` 的本地 `slug()` 完全不知道 `normalizeId` 的守卫修过。
- **修法**：「归一化丢过信息就必须补短哈希」；`capture.js` 删掉本地 `slug()`，强制走 `normalizeId`（`lib/model.js:115-144`、`lib/capture.js:297-307`）。
- **回归**：`test/capture.test.mjs` · 「自动分配 id」。

### 7.7 每条 `file:line` 锚点在干净工作树上都报假 `advisory`

- **现象**：带行号的锚点 100% 报「切片变了」。每一次重构都把整库标成不可信，然后所有人学会忽略这个警告。
- **根因**：**写入侧哈希整个文件、复查侧哈希行切片** —— 两侧各写一套，永远对不上。
- **修法**：抽出 `lib/anchor.js` 作为**唯一事实源**（叶子模块，避免 `gate ↔ drift` 循环）；`symbol` 锚点在写入侧**真的去算哈希**（`lib/anchor.js`、`lib/gate.js:413-416`、`lib/drift.js:32`）。
- **回归**：`test/anchor.test.mjs` · 「只依赖切片内容：同行号 → 同哈希；不同切片 → 不同哈希」；`test/drift.test.mjs` · 「**文件没改 → healthy**」「BOM 文件：gate 写入的哈希在 drift 侧仍然 healthy」。

### 7.8 召回 token 预算完全失效（+ ngram 恒空 + `threshold` 是 `NaN`）

三个独立的「算错了但没人报错」：

| 部件 | 错在哪 | 修法 |
|---|---|---|
| 预算 | `estimatedTokens` 按**全文**记，却把**全文**也注入 —— 预算从来没裁过任何东西 | 按**实际注入的节选**算（`lib/recall.js:649`） |
| ngram 路 | 分母被文档长度主导，`< 0.45` 这类门槛**数学上永远达不到** | 改覆盖率定义（`lib/recall.js:288`） |
| 特征集 | 按对象读，`exact` / `graph` 两条恒为 `undefined` | 按 Map 读（`lib/recall.js:402`） |
| `threshold` | 默认 `config = {}` 时是 `NaN`，比较恒 false → 什么都不交付 | 只给部分标签时落到 0.65 兜底 |

- **回归**：`test/recall.test.mjs` · 「注入的是节选不是全文，estimatedTokens 按实际注入量算」「配置只给了部分标签时落到 0.65 兜底（不是 NaN）」「**exact 命中的 anchor 特征真的进特征集**（曾经恒为 undefined）」。
