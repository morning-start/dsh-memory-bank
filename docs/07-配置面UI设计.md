## 0 · 结论先行

三件事，按依赖顺序：

| # | 结论 | 为什么 |
|---|---|---|
| **1** | 配置是**两层**的，不是一层 | DSH 的插件配置是 **profile 级**（`~/.dsh/profiles/...`），而记忆库是**仓库级**（`<repo>/.dsh-memory/`）。把「这个仓库要不要开自动捕获」写进 profile，换仓库就串味 |
| **2** | 需要**两个**界面，不是一个 | ① **插件配置卡片**（`plugins.item` slot，走 DSH 原生设置页，复用 `ctx.configForms`）② **记忆面板**（`main` + `sidebar.panellist`，自绘） |
| **3** | 有 **3 个前置缺口**必须先补 | 项目配置 `.dsh-memory/config.json` **从不读写**；`resolveConfig` **没有第三层**；`cfg` 是 `apply()` 的闭包，**改了不生效**。不补这三条，UI 就是空中楼阁 |

## 1 · 现状（代码事实，非推测）

### 1.1 配置的三层，只有两层是活的

`lib/config.js` 声称「行 config > 环境变量 > 默认值」：

```js
// lib/config.js:90
const merged = deepMerge(deepMerge(defaults, envLayer(env)), rowConfig)
```

**第三层（项目配置）不存在。** 证据：

```
$ rg 'config\.json' lib/
lib/store.js:7:   *   ├── config.json          本项目配置
lib/store.js:40:    config: join(base, 'config.json'),
```

`layout()` 声明了这个路径，**全仓没有任何代码读或写它**。所以：

- 用户按 `docs/06` 改 `.dsh-memory/config.json` → **完全不生效**，也没有任何提示；
- 「这个仓库关掉自动捕获」做不到——只能改 profile，影响所有仓库。

### 1.2 配置改了不会生效

`lib/index.js:170-171` 的 `apply(ctx, config)` 里：

```js
export function apply(ctx, config) {
  const cfg = resolveConfig(config ?? {})   // 只算一次
```

`cfg` 是一个**冻结的普通对象**，被 7 个工具、2 个钩子、1 个命令闭包捕获。改任何持久化层都不会重新 `resolveConfig`，**必须重启宿主**。

### 1.3 今天的配置入口

| 入口 | 能力 | 缺口 |
|---|---|---|
| `cordis.patch.yml` 的 `config:` | 全部字段 | 手写 YAML，无校验提示，无枚举补全 |
| `DSH_MEMORY_*` 环境变量 | 4 个 | 全局生效，无法按仓库覆盖 |
| `/memory` 命令 | 只读状态 | 不能改配置 |
| 7 个 `memory_*` 工具 | 数据面 | 不碰配置 |

**结论：没有任何一个入口能按仓库改配置。**

## 2 · DSH 插件 UI 能力（已从宿主源码验证）

> 源码快照：`~/.dsh/profiles/desktop/node_modules/@deepseek-ai/dsh-desktop-runtime/refs/host-src/dsh/dsh/node_modules/@deepseek-ai/`
> 下面每条都标了 `包/文件:行`，可复核。

### 2.1 客户端模块协议

客户端 bundle 不是 ES module，而是一个**全局注册调用**：

```js
// dsh-client-ui-settings-plugins/lib/client.js:1-5
window.__ModuleLoader__.load({
  id: '@deepseek-ai/dsh-client-ui-settings-plugins',
  factory: (require) => {
    var module = { exports: {} }
    var exports = module.exports
    // 这里可以 require('react') / require('@deepseek-ai/dsh-client-ui-primitives')
    exports.apply = apply
    exports.inject = inject
    return module.exports
  },
})
```

**关键约束**（`dsh-client-modules` 的 `resolveMeta → exactPackageSpecifier`）：只有**裸包名**（不含 `/`）的行才会进 `window.__DSH_BOOT__` 客户端图。`dsh-plugin-myteam/panel` 这种子路径**不进图，面板整体不可见**。

### 2.2 Slot 系统

ctx.slots.inject(slotName, () => ctx.slots.register(options, Component))
ctx.slots.entries(slotName)          // 列注册项
ctx.slots.getVersion(slotName)       // 版本号（配合 useSyncExternalStore）
ctx.slots.subscribe(slotName, cb)    // 订阅变化

### 2.3 配置表单（**这是「配置改用 UI」的正解**）

宿主**自己拥有**配置值，插件只渲染控件：

```js
// ui-settings-agent-loop/lib/client.js:139-165
const inject = ['slots', 'locale', 'configForms']

function apply(ctx) {
  const t = ctx.locale.bind(NS)
  ctx.effect(() => ctx.locale.register(NS, { zh, en }), 'dictionaries')

  const card = new CardController(ctx.configForms.get('agent-loop'))
  ctx.effect(() => () => card.dispose(), 'form subscription')

  ctx.effect(() => ctx.configForms.whileServed(['agent-loop'], () =>
    ctx.slots.inject('plugins.item', () => ctx.slots.register({
      name: 'plugins.item',
      id: 'agent-loop',
      order: 30,
      label: () => t('title'),
      locale: NS,
      inject: () => card.inject(),
    }, AgentLoopCard))
  ), 'page')
}
```

渲染用宿主提供的原语（`@deepseek-ai/dsh-client-ui-primitives`，**运行时注入，不打包**）：

```js
<SettingsForm labels state onSave={props.save} onDiscard={props.discard}>
  <SettingsValueField
    id="..." label={t('...')} hint={t('...')}
    numeric disabled={!state.writable}
    {...state.maxParallelToolCalls}
    onEdit={(text) => props.edit('maxParallelToolCalls', text)}
    onReset={() => props.resetField('maxParallelToolCalls')}
  />
</SettingsForm>
```

**含义**：配置的**读写、暂存（staged）、保存、丢弃、重置、校验、越权提示**全部由宿主负责。我们只需要：

1. 在 `Config` 里声明字段（schemastery）；
2. 写一个卡片组件，把字段绑到 `SettingsValueField`；
3. 用 `ctx.configForms.get(namespace)` 拿到 scope。

### 阶段 A · 配置域（`lib/config/`）

> **前置中的前置。** 没有这一层，UI 保存的配置没有地方落、落了不生效。

| 模块 | 职责 | 关键点 |
|---|---|---|
| **A1 `schema.js`** | 配置 schema 的**单一事实源** | 从 `lib/index.js` 的 `Config` 抽出。**host 与 client 都要 import 它**——两边各写一份就是漂移。schemastery 是 peer 依赖，服务端可用；客户端拿不到时降级为「只渲染、不校验」 |
| **A2 `defaults.js`** | 默认值 | 从 `store.defaultConfig()` 抽出。`schema` 里**故意不填 `.default()`**（填了会永久遮蔽环境变量回退，`lib/config.js:1-6` 已经踩过） |
| **A3 `layers.js`** | 四层合并：**默认 → 项目 → 环境 → 行 config** | 0.1.1 修的是「默认 → 环境 → 行」，现在把**项目层插在环境变量之前**——项目配置比 `DSH_MEMORY_*` 更具体？**反了。** 环境变量是「这台机器的临时覆盖」，应该最高。见下方 §4 的决定 |
| **A4 `project.js`** | `<repo>/.dsh-memory/config.json` 读写 | 原子写（`writeFileAtomic`）+ 读时 schema 校验 + 坏文件降级为默认值**并报 `problems`**（不静默） |
| **A5 `migrate.js`** | `schemaVersion` 迁移 | 已有 `config.version: 1`。加版本判定 + 迁移函数表 |
| **A6 `index.js`** | 对外门面：`getConfig(root)` / `setConfig(root, patch)` / `subscribe(root, cb)` | **`getConfig` 带缓存**（按 `contentHash(config.json)` 失效），避免每次工具调用读盘 |

**A3 的决定**（写进 ADR）：

```
行 config（cordis.patch.yml）  ← 最高：部署者显式指定
    > 环境变量 DSH_MEMORY_*     ← 次高：本机临时覆盖
    > 项目 .dsh-memory/config.json  ← 团队共享：进 git
    > 内置默认值                ← 兜底
```

> 为什么项目层**低于**环境变量：`.dsh-memory/config.json` 进 git、随 PR review，是**团队共识**；`DSH_MEMORY_*` 是**这台机器**的临时状态（CI、调试）。临时状态应该能盖过共识，但**不能**盖过部署者在 patch 里的显式配置。

## 4 · 界面规格（三个界面）

> 只定义**信息架构**，视觉在下个会话做。

### 界面 1 · 配置卡片（`plugins.item`）

**位置**：设置 → 插件 → 「官方插件」组的 `memory-bank` 卡片 → 点「配置」。

**结构**：按 `Config` 的顶层键分 6 组，每组一个可折叠区块：

| 组 | 字段 | 控件 |
|---|---|---|
| **自主度** | `autonomy` | 三选一（manual / balanced / autonomous）+ 每个选项一行说明 |
| **审核阈值** | `thresholds.*` | 6 个 0–1 数值 + 一个「显示高级（`thresholds.content`）」折叠 |
| **捕获** | `capture.enabled` · `mode` · `draft` · `signals` | 开关 + 二选一 + 二选一 + 6 个多选 |
| **召回** | `recall.inject` · `maxBytes` · `maxPointers` | 开关 + 数值 + 数值 |
| **配额** | `quota.repo` · `growthThreshold` | 两个数值 |
| **高级** | `template` · `safety.forbidden` · `conflict.semantic` · `embedding.*` | 数组编辑 + 数组编辑 + 开关 + 只读展示（`provider` 默认 `none`，开闸要跑 bench） |

**每条字段必须显示**：

- 当前值 + 默认值（如 `0.60`）；
- **来源徽标**（`default` / `project` / `env` / `row`）—— 非 `project` 时输入框 `disabled` 并给 tooltip「来自环境变量，改这里不生效」；
- 一行 hint（复用 `Config` 里现有的 `description`，那是已经写好的中文）。

**保存语义**：走宿主的 staged form（`save` / `discard` / `resetField`），**不自己实现**。

### 界面 2 · 记忆面板（`main` + `sidebar.panellist`）

**位置**：左侧导航「记忆」图标。

**顶部**：一行健康概览（**只读**，来自 `overview()`）

```
活跃 42 · 待决 3 · 队列 0 · 坏文件 1    │  open 7（可行动 3） · 矛盾 2    │  休眠 9 · 到期 4    │  配额 42/50
```

**下面四个 tab**：

| tab | 内容 | 动作 |
|---|---|---|
| **待决**（默认，有积压时高亮） | 提案列表：id · kind · title · 判不了的门 · 置信 | 展开详情 → accept / reject / edit |
| **记忆** | 搜索框 + 列表（title · kind · 最后召回 · 状态） | 详情 → retire / forget |
| **漂移** | 三个桶：`quarantined`（红）/ `advisory`（黄）/ `unsafe-path`（红） | 点锚点 → 打开文件 |
| **审计** | ledger 时间线（ACCEPT / REJECT / DEFER / discard） | 只读 |

**空态文案**（重要，比按钮更常被看到）：

- 待决为空 → 「没有待决提案。协议判不了的会出现在这里。」+ 一行「为什么会有积压？」的链接
- 漂移为空 → 「锚点全部健康（N 条）。」
- 队列 > 0 → 一条 warning：「后台队列还有 N 条未处理。它们已经落盘，重启后仍在 `.dsh-memory/inbox/`。」

### 界面 3 · 项目配置（**新**）

**位置**：界面 2 的「记忆」tab 右上角，一个「项目配置」按钮 → 抽屉。

**为什么单独做**：界面 1 是 **profile 级**（`~/.dsh/...`），界面 3 是 **仓库级**（`<repo>/.dsh-memory/config.json`）。同一个字段在两个界面里都出现时，**必须能看出哪个生效**。

**内容**：只有「值得按仓库不同」的字段：

```jsonc
{
  "schemaVersion": 1,
  "capture": { "enabled": false },        // 这个仓库关掉自动捕获
  "quota": { "repo": 50 },                // 这个仓库小一点
  "template": ["功能名", "..."],           // 这个仓库的六要素叫法不同
  "safety": { "forbidden": ["CUSTOM_\\d{8}"] }
}
```

**不放在这里**的：`autonomy` / `thresholds` / `embedding` —— 那些是**用户偏好**，不是仓库属性。

> 这条边界要写死。否则「为什么我的配置在这个仓库不生效」会变成最常见的支持问题。

## 5 · 分阶段落地

| 阶段 | 内容 | 产出 | 验收 |
|---|---|---|---|
| **P0** | 补 3 个前置缺口（§1.1 / §1.2） | `lib/config/`（A1–A6）+ `test/config.test.mjs` | `.dsh-memory/config.json` 改了**真的生效**；`resolveConfig` 有四层；`subscribe` 能触发重载 |
| **P1** | 配置卡片（界面 1） | `client/index.js` + `ConfigCard` | 设置页能看到卡片；改 `autonomy` 保存后 `/memory status` 反映出来；env 层字段显示为只读 |
| **P2** | 只读面板（界面 2 的「漂移」「审计」） | `lib/host/queries.js` + `MemoryPanel` 两个 tab | 面板上的数字与 `/memory audit` **逐字一致** |
| **P3** | 裁决（界面 2 的「待决」） | `lib/host/mutations.js` + `PendingList` | 面板 accept 一条 → 文件出现、`memory_recall` 能召回；reject → 进 `pending/rejected/` |
| **P4** | 项目配置（界面 3） | 抽屉 + `project.js` 的写路径 | 改 `capture.enabled` 只影响这个仓库 |

**每阶段的验收都必须能一条命令复现**（`node --test` / `node bench/acceptance.mjs`），否则不算完成——0.1.0 的「196 条全绿」教训。

## 6 · 风险与未决

| 风险 | 影响 | 缓解 |
|---|---|---|
| **`ConfigPageForm` 契约未完全验证** | P1 可能做不下去 | 下个会话**先做一次探针**（§2.6），30 分钟内能确认 |
| **`dsh-client-ui-primitives` 的字段类型不全** | 枚举/布尔/数组可能没有对应原语 | 降级：用 `<SettingsValueField>` + 自绘；最坏情况整个卡片自绘，只是失去 staged form |
| **客户端 bundle 破坏「无构建」** | 工程复杂度上升 | P1 手写 `React.createElement` 验证可行性，再决定是否上 esbuild |
| **两层配置的认知负担** | 用户困惑「为什么改了不生效」 | 界面 1 的**来源徽标** + 界面 3 的**边界文案**是硬要求，不是锦上添花 |
| **面板与命令面双实现漂移** | 又一类「两套实现」bug | `lib/command.js` 重构成薄壳，共用 `lib/host/mutations.js`；`test/wiring.test.mjs` 加一条「命令面与面板面调用同一函数」 |
| **`ctx.configForms` 是可选服务** | headless / sdk profile 里没有 | 与 `commands` / `userQuestions` 同样处理：`ctx.inject(['configForms'])`，拿不到就只挂面板、不挂配置卡片 |

## 8 · 一句话

> **配置 UI 不是「把 yaml 变成表单」，是「让用户看得见哪一层在生效」。**
>
> 0.1.1 修的三个配置缺陷（环境变量全死、默认值遮蔽、`config.json` 不读）本质上都是同一件事：
> **作用域不可见**。UI 的第一职责是把作用域画出来，第二职责才是省掉手写 yaml。
