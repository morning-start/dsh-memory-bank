## 1 · 现状（代码事实，非推测）

> **本节记录的是 0.1.1 结束时的状态，用于说明为什么需要 P0。**
> 三个缺口在 0.2.0 的 P0 里已经补上（提交 `f9f9cc6`），逐条见 §5 的 P0 行。

### 1.1 配置的三层，只有两层是活的

`lib/config.js:90`：

```js
const merged = deepMerge(deepMerge(defaults, envLayer(env)), rowConfig)
```

**第三层（项目配置）不存在。** 证据：

```
$ rg 'config\.json' lib/
lib/store.js:7:   *   ├── config.json          本项目配置
lib/store.js:40:    config: join(base, 'config.json'),
```

`layout()` 声明了这个路径，**全仓没有任何代码读或写它**。所以用户按 `docs/06` 改 `.dsh-memory/config.json` → **完全不生效，也没有任何提示**。

> 现在：`lib/config/project.js` 读写这一层，坏文件降级为默认值**并报 `problems`**（不静默）。
> 合并顺序见 `lib/config/layers.js` 文件头。

### 1.2 配置改了不生效

`lib/index.js:170-171`：

```js
export function apply(ctx, config) {
  const cfg = resolveConfig(config ?? {})   // 只算一次
```

`cfg` 被 7 个工具、2 个钩子、1 个命令闭包捕获。改任何持久化层都不会重新 `resolveConfig`，**必须重启宿主**。

> 现在：`cfg` 闭包换成 `createConfigSource({ rowConfig })`，每个消费者
> `configSource.get(root)`，按 `mtime:size` 失效。保存即生效。

### 1.3 当时的配置入口

| 入口 | 能力 | 缺口 |
|---|---|---|
| `cordis.patch.yml` 的 `config:` | 全部字段 | 手写 YAML，无校验提示，无枚举补全 |
| `DSH_MEMORY_*` 环境变量 | 4 个 | 全局生效，无法按仓库覆盖 |
| `/memory` 命令 | 只读状态 | 不能改配置 |

**结论：没有任何一个入口能按仓库改配置。** —— 这就是这一版要做的全部理由。

### 2.3 配置表单：**没有自动渲染，必须手写**

`dsh-settings/README.md:39` 明说 `autoGenerate` 「no shipped client does so yet」。官方 5 个设置页（`ui-settings-general` / `models` / `account` / `agent-loop` / `session-log`）全部**手写**控件。

**而且只有 `.volatile()` 字段可编辑**（`dsh-settings/lib/types/schema.js:43-54` 的 `volatileForm`）：

```js
export function volatileForm(schema) {
  if (schema.meta.volatile) return plainSchema(schema)
  if (schema.type === 'object') {
    const dict = Object.fromEntries(Object.entries(schema.dict ?? {}).flatMap(([key, child]) => {
      const field = volatileForm(child)
      return field === undefined ? [] : [[key, field]]
    }))
    return Object.keys(dict).length === 0 ? undefined : z.object(dict)
  }
  return undefined
}
```

**这是本设计最容易被忽略的一条**：`lib/index.js` 的 `Config` 现在**一个字段都没标 `.volatile()`**，照现状直接接 UI，**整张表单只读**，而且宿主不会告诉你为什么。

> **§2.9 ③：这条的「硬门」定性要说准。** `.volatile()` 本身是可选的
> schemastery 修饰符；它**只对**「挂 `plugins.*.config` 让宿主渲染配置表单」
> 这件事是硬门（`dsh-settings/lib/index.js:353` 会抛
> `'Plugin entry "<ns>" has no volatile fields'`）。只挂 `settings.section`
> 的插件不需要它。

**已实测坐实**（`node .tmp-probe/volatile.mjs`）：

```
Config 顶层键 = root, autonomy, thresholds, template, safety, conflict, quota, capture, recall, promote, embedding

volatileForm(Config) = undefined   ← 整张只读

--- 逐字段 ---
  root           volatile=false type=string
  autonomy       volatile=false type=union
  thresholds     volatile=false type=object
  ...（11 个全部 false）

--- 标了 .volatile() 之后 ---
volatileForm(Demo) = z.object({...})
  可编辑字段 = autonomy, thresholds
  plain 被排除 = true
```

`.volatile()` 可以标在**父对象**上（递归生效），所以最小改动是：

```js
export const Config = z.object({
  autonomy: z.union([...]).volatile(),      // 单字段
  thresholds: z.object({...}).volatile(),   // 整棵子树
  ...
})
```

**并且**：`practices.md:35` 明令**禁止** `require('@deepseek-ai/dsh-client-ui-primitives')` —— 那些组件会随版本静默变。要**手写控件并复制宿主的 markup / CSS / 行为**（见 §2.6）。

### 2.5 服务端 → 客户端通信

> **§2.9 ④：这一节初版写「零 codegen」，是过度乐观。** 下面是最小可跑的形态，
> 但三个环节缺一不可（生成产物 / `exports` / `dsh.client.inject`），
> 而生成产物是**纯数据**，可以手写。完整论证见 §2.9 ④。

**客户端不手调 `connection.rpc.call`，走生成的服务面**：

```js
// 客户端：ctx.remote.<namespace>.<method>()
const snapshot = await ctx.remote.memoryBank.overview()
```

```js
// 服务端：TypertRemoteService 子类，namespace 就是 Cordis 服务键
import { TypertRemoteService } from '@deepseek-ai/dsh-typert-protocol'
class MemoryPanelService extends TypertRemoteService {
  constructor(ctx, config) { super(ctx, 'memoryBank'); this.config = config }
  async overview() { /* ... */ }
}
export { MemoryPanelService as default }
```

线上方法名 = `<namespace>/<method>`（`dsh-typert-protocol/lib/index.js:329` 的
`options.namespace ?? serviceKey`），所以 `overview` → `memoryBank/overview`。
命名空间段必须匹配 `/^[A-Za-z0-9_$.-]+$/` 且不是 `.` / `..`（`:306-311`）。

**不要**去碰 `dsh-typert-protocol` 的**生成器**（codegen）——只有运行时基类要用。

### 2.9 返工记录（实施前源码复核）

复核方式：把宿主快照里**每一个**相关包读一遍，逐条标 `文件:行`。
下面三条是**本文初版的错误结论**，照做会静默失败或平白多干一周活。

#### ① `main` 槽 —— 初版说「禁用」，**错在过度保守**

初版写「`main` 的 `replaceRisk: shadows-shipped-ui` —— 注册就替换宿主中央面板」。
源码（`dsh-cordis-client-runner/lib/client.js:4370-4396`）不是这个意思：

```js
key: "main", kind: "keyed",
keyDomain: "open: any string the owner dispatches (no compile-time key set), already taken: conversation",
replaceRisk: "shadows-shipped-ui",
```

`shadows-shipped-ui` 只对**已被占用的 key** 生效 —— 也就是 `conversation`
（以及 `plugins.*` 那几个 `main` 里的自带页面）。**用一个全新的 key 注册是纯加法**，
和别的 keyed 槽没有区别。官方 `dsh-client-ui-plugin-manager` 自己就是这么做的
（`lib/client.js:4411-4417`）。

**结论不变，理由要改**：我们仍然用 `settings.section`，不是因为 `main` 危险，
而是因为「记忆面板」本来就是设置页里的一栏 —— 放进 `main` 会**多开一个
侧栏入口**去承载一个没有独立工作流的只读列表。这是产品判断，不是安全约束。

#### ② `require('@deepseek-ai/*')` —— 初版说「禁止」，**错在过度保守**

`practices.md:35` 的原话是「Do not `require('@deepseek-ai/dsh-client-ui-primitives')`
**or load any other Harness Client package as a module**」。但宿主的模块表里
有 **11 个种子词**，`require` 它们**零声明即可用**，官方包自己就在用：

```js
// dsh-client-ui-settings-web-search/lib/client.js:7-9
let _deepseek_ai_dsh_client_ui_primitives = require("@deepseek-ai/dsh-client-ui-primitives");
let _deepseek_ai_dsh_client_store = require("@deepseek-ai/dsh-client-store");
```

种子词：`@deepseek-ai/cordis` / `dsh-client-store` / `dsh-client-ui-slots` /
`dsh-client-ui-primitives` / `dsh-client-ui-dockkit` / `react` / `react/jsx-runtime` 等。
**表外**的包才需要 `dsh.client.external` + 活的 boot 图行，否则 `require` 抛
（`dsh-client-modules/lib/client.js:840`）。

**结论不变，理由要改**：我们仍然手写控件。理由是 `practices.md:35` 紧接着那句 ——
「They change without notice, a plain-JS plugin has no type check, and a throwing
component blanks your slot entry」。**能 require 不等于该 require**：
第三方插件没有类型检查，宿主一升级就是整片白。这条是**策略**，不是平台限制。

> 代价要认：手写 `Switch` / `TextField` / `Modal` 的焦点、Escape、`role="switch"`
> `aria-checked` 是这一版最大的工作量来源。`design/app.css` 已经是照宿主抄好的实现。

#### ③ `.volatile()` —— 初版说「硬门」，**说对了结果，说错了性质**

`.volatile()` 本身是 schemastery 的**选择性**修饰符（`schemastery/src/index.ts:235-238`），
不加也能解析。它的作用只有一个：**变更时不重挂插件**（`cordis-plugin-loader/README.md:53`
的 `_commitVolatile` / `loader/volatile-update`）。

但**对我们要做的这两个界面，它确实是硬门** —— 因为 `dsh-settings` 的配置表单是
按 `volatileForm(schema)` 裁的，一个 volatile 字段都没有时直接抛：

```js
// dsh-settings/lib/index.js:353
throw new Error(`Plugin entry "${ns}" has no volatile fields`);
```

而我们注册的正是 `plugins.item` / `plugins.row.config`。所以：

- 挂 `plugins.*.config` → **必须** `.volatile()`；
- 只挂 `settings.section`（不接宿主的配置表单）→ 不需要。

**结论不变**：11 个顶层键全部标了 `.volatile()`。但要知道它现在的副作用 ——
schema 解析出的值是 `Volatile<T>` 引用，`apply()` 里**必须先 `plainConfig()`
才能合并**（见 §2.9 ④）。

#### ④ 新增：RPC 不是「零 codegen」

初版 §2.5 写「零 codegen 的 RPC，`myteam/plugin/client/client.js:2651` 已跑通」。
复核后这条**过度乐观**：

- 线上方法名确实是 `<namespace>/<method>`（`dsh-typert-protocol/lib/index.js:329`
  的 `options.namespace ?? serviceKey`），**命名规则这条是对的**；
- 但客户端**不该**手调 `connection.rpc.call`，而应走 `ctx.remote.memoryBank.*`；
- 而 `ctx.remote.*` 的 spec 来自**生成产物** `lib/typert.host.js` +
  `lib/typert.remote-client.js`（`@deepseek-ai/dsh-typert-generator` 生成），
  `package.json` 必须同时导出 `./typert` 和 `./remote`；
- **客户端**还要 `inject: ['remote', 'remote.memoryBank']`，且 `dsh.client.inject`
  必须列出 `@deepseek-ai/dsh-api-remotes`（激活顺序）。

也就是三个环节缺一不可。好在生成产物是**纯数据**（2.9 KB，`createTypertRemoteInfo`
+ JSON Schema），**可以手写**，不需要引入生成器。这一条已落到
`lib/typert.host.js` / `lib/typert.remote-client.js`。

#### ⑤ 新增：`schemastery` 会把「没提供」物化成空容器

复核时跑出来的一个**静默数据丢失**（不是文档错，是实现陷阱）：

```js
plainConfig(Config({ autonomy: 'balanced' }))
// => { autonomy: 'balanced', template: [], capture: { signals: [] }, safety: { forbidden: [] }, ... }
```

`deepMerge` 对数组是**整体替换**。于是 `template: []` → 六要素门对每一条记忆
refuse，`capture.signals: []` → 自动捕获永不触发，**而且没有任何报错**。

修法：`lib/config/layers.js` 的 `pruneMaterialized` 在合并前裁掉 schema 物化出来的
空容器。测试：`test/config.test.mjs` 的「宿主交进来的解析值不会静默清空默认值」。

**ADR-001 · 层级顺序**

```
行 config（cordis.patch.yml）      ← 最高：部署者显式指定
    > 环境变量 DSH_MEMORY_*        ← 次高：本机临时覆盖（CI / 调试）
    > 项目 .dsh-memory/config.json ← 团队共识：进 git、随 PR review
    > 内置默认值                    ← 兜底
```

> 临时状态应该能盖过共识，但**不能**盖过部署者在 patch 里的显式配置。

**ADR-002 · 配置变更的生效语义**

`cfg` 现在是 `apply()` 的闭包。两个选项：

| 方案 | 代价 | 决定 |
|---|---|---|
| 把 `cfg` 改成 `() => cfg` + 重新 resolve | 7 个工具 + 2 个钩子 + 1 个命令全部改签名 | ❌ 改动面太大 |
| **`getConfig(root)` 每次调用时读缓存** | 每次工具调用多一次缓存查找（< 1 µs） | ✅ 采用 |

**A6 的 `getConfig` 是热重载的唯一入口**：所有消费者从 `cfg` 改成 `getConfig(root)`，配置一变立刻生效。

**C1 骨架**：

```js
const NS = 'memoryBank'

export const inject = ['slots', 'locale', 'connection']

export function apply(ctx) {
  const t = ctx.locale.bind(NS)
  ctx.effect(() => ctx.locale.register(NS, { zh, en }), 'memory-bank: dictionaries')

  // ① 配置卡片（Plugins 页「官方插件」组）
  ctx.slots.inject('plugins.item', () => ctx.slots.register({
    name: 'plugins.item',
    id: 'memory-bank',
    order: 60,
    label: () => t('configTitle'),
    locale: NS,
    inject: () => ({ ctx, connection: ctx.connection, t }),
  }, ConfigCard))

  // ② 「记忆」设置页（settings.section 是加法槽，replaceRisk: none）
  ctx.slots.inject('settings.section', () => ctx.slots.register({
    name: 'settings.section',
    id: 'memory-bank',
    order: 40,
    label: () => t('panelTitle'),
    locale: NS,
    inject: () => ({ ctx, connection: ctx.connection, t }),
  }, MemorySection))
}
```

**注意**：`ctx.slots.inject` 的回调会被**反复调用**（槽塌陷/恢复），所以里面**不能有副作用**，且 `apply` 里加的资源都返回清理函数。

> 只定义**信息架构**，视觉在下个会话做。

### 界面 1 · 配置卡片（`plugins.item` + `plugins.row.config`）

**位置**：设置 → 插件 → 「官方插件」组的 `memory-bank` 卡片 → 点「配置」。

**结构**：按 `Config` 的顶层键分 6 组，每组一个可折叠区块：

| 组 | 字段 | 控件（**手写**，照抄宿主样式） |
|---|---|---|
| **自主度** | `autonomy` | 三选一（manual / balanced / autonomous）+ 每个选项一行说明 |
| **审核阈值** | `thresholds.*` | 6 个 0–1 数值 + 「显示高级（`thresholds.content`）」折叠 |
| **捕获** | `capture.enabled` · `mode` · `draft` · `signals` | 开关 + 二选一 + 二选一 + 6 个多选 |
| **召回** | `recall.inject` · `maxBytes` · `maxPointers` | 开关 + 数值 + 数值 |
| **配额** | `quota.repo` · `growthThreshold` | 两个数值 |
| **高级** | `template` · `safety.forbidden` · `conflict.semantic` · `embedding.*` | 数组编辑 + 数组编辑 + 开关 + 只读展示（`provider` 默认 `none`，开闸要跑 bench） |

**每条字段必须显示**：

- 当前值 + 默认值（如 `0.60`）；
- **来源徽标**（`default` / `project` / `env` / `row`）—— 非 `project` 时输入框 `disabled` 并给 tooltip「来自环境变量，改这里不生效」；
- 一行 hint（复用 `Config` 里现有的 `description`，那是已经写好的中文）。

**保存语义**：手写 staged form（`draft` 状态 + 保存/放弃/重置三个动作）。宿主**不提供** `SettingsFormModel` —— 那是 Harness Client 内部包，禁止 require。

### 界面 2 · 「记忆」设置页（`settings.section`）

**位置**：设置 → 记忆。

**顶部**：一行健康概览（**只读**，来自 `memoryBank/overview`）

```
活跃 42 · 待决 3 · 队列 0 · 坏文件 1    │  open 7（可行动 3） · 矛盾 2    │  休眠 9 · 到期 4    │  配额 42/50
```

**下面四个 tab**：

| tab | 内容 | 动作 |
|---|---|---|
| **待决**（默认，有积压时高亮） | 提案列表：id · kind · title · 判不了的门 · 置信 | 展开详情 → accept / reject / edit |
| **记忆** | 搜索框 + 列表（title · kind · 最后召回 · 状态） | 详情 → retire / forget |
| **漂移** | 三个桶：`quarantined`（红）/ `advisory`（黄）/ `unsafe-path`（红） | 点锚点 → 打开文件 |
| **审计** | ledger 时间线（ACCEPT / REJECT / DEFER / discard） | 只读 |

**待决提醒**：有待决时，通过 `shell.overlay`（`replaceRisk: none`）弹一条 toast，带「去看」按钮 → `ctx.layout.selectPanel(...)` + 定位到设置页。

**空态文案**（比按钮更常被看到）：

- 待决为空 → 「没有待决提案。协议判不了的会出现在这里。」+ 一行「为什么会有积压？」的链接
- 漂移为空 → 「锚点全部健康（N 条）。」
- 队列 > 0 → 一条 warning：「后台队列还有 N 条未处理。它们已经落盘，重启后仍在 `.dsh-memory/inbox/`。」

### 界面 3 · 项目配置（**新**，界面 2 的「记忆」tab 里的抽屉）

**为什么单独做**：界面 1 是 **profile 级**（`~/.dsh/...`），界面 3 是 **仓库级**（`<repo>/.dsh-memory/config.json`）。同一个字段在两个界面里都出现时，**必须能看出哪个生效**。

**内容**：只有「值得按仓库不同」的字段：

```jsonc
{
  "schemaVersion": 1,
  "capture": { "enabled": false },        // 这个仓库关掉自动捕获
  "quota": { "repo": 50 },                // 这个仓库小一点
  "template": ["功能名", "..."],           // 这个仓库的六要素叫法不同
  "safety": { "forbidden": ["CUSTOM_\\d{8}"] }
}
```

**不放在这里**的：`autonomy` / `thresholds` / `embedding` —— 那些是**用户偏好**，不是仓库属性。

> 这条边界要写死。否则「为什么我的配置在这个仓库不生效」会变成最常见的支持问题。

```
- 不要 require 任何 @deepseek-ai/* Client 包（practices.md:35 明令禁止）
- Config 字段必须标 .volatile()，否则 UI 整张只读
- Loader 行的 name 必须是裸包名，子路径静默不进客户端图

从 P0 开始（补 4 个前置缺口）。P0 的第一件事是给 lib/index.js 的 Config
加 .volatile()，并写一条 volatileForm(Config) !== undefined 的断言。

起点代码：cp -r <官方指南>/templates/decoration/* client/
```

## 8 · 一句话

> **配置 UI 不是「把 yaml 变成表单」，是「让用户看得见哪一层在生效」。**
>
> 0.1.1 修的三个配置缺陷（环境变量全死、默认值遮蔽、`config.json` 不读）本质上都是同一件事：
> **作用域不可见**。UI 的第一职责是把作用域画出来，第二职责才是省掉手写 yaml。
>
> 而这一版设计最大的收获是**两条否定**：不能用 `main`（会劫持界面），不能 require 宿主组件（会静默崩）。
> 剩下的都是体力活。
